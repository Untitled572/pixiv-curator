## 已确认问题

### 1. 真实关注列表会被默认头像阻断

失败游标为公开关注列表 offset=60。诊断重新取得该页：30 位画师，下一页 offset=90，游标正常前进；其中第 28 位画师 ID 有效，但头像来自 HTTPS s.pximg.net。

[NormalizeArtist](../internal/pixiv/models.go) 使用 [ValidImageURL](../internal/domain/media.go) 校验头像，而该校验仅允许 i.pximg.net。于是这一合法用户被映射成 ErrInvalid，再由 [关注采集](../internal/app/ingest.go) 转为 INVALID_TASK，整页被拒绝、快照不能完成。这不是 OAuth 失败，也不是分页游标循环。

建议把头像与作品原图 URL 的校验规则区分开；只明确接受已确认用途的官方头像地址。不要为修复头像而放宽原图目标白名单，也不要把失效头像当成整页关注数据无效。修复后应回归默认头像、异常用户、完整关注快照和中断恢复，并重新执行实网全量同步。

### 2. Windows 二进制可编译但无法启动

[sqlite.Open](../internal/store/sqlite/store.go) 将 Windows 绝对路径直接作为 URL.Path，生成错误的 file URI。Windows 临时数据库启动实测退出码 1，错误为 invalid uri authority: C:；依赖数据库的测试也因此失败。由于实现始终先 filepath.Abs，改成相对配置路径也不能解决此问题。

另外两项 Pixiv 测试分别依赖 Unix 权限位和创建符号链接的权限，当前 Windows 环境不满足。应分别处理路径 URI 兼容与测试的平台语义，不能把四平台“编译成功”当作 Windows 运行通过。

### 3. 返回 URL 与消费端图片可用是两步

当前 Curator 不代理图片字节，消费端需要自己的可达网络和正确 Referer。本次同图请求的 403 / 206 对比确认了这一点。管理页预览通过固定预览端点 302 跳转图片域名；此次没有完成真实浏览器预览或 PicHub 下载验收，不能从后端 URL 返回成功推断页面图片一定可显示。

## 推荐的当前边界

推荐从远端关注或本地 approved 画师中按 ID 取最多 30 位种子，通过 Pixiv 相关画师、相关作品召回候选，再按标签、来源证据和收藏质量进行可解释排序；不是视觉模型。最多 60 位候选、每候选 4 件样本，总请求预算 300。当前种子按 ID 截取，关注较多时覆盖有限；可识别的来源常量不等于已实现推荐流或标签搜索召回。
